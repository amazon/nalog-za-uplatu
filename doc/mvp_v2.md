# Samo IPS — Corrected MVP Application Specification

## 1. Product identity

**Product name:** Samo IPS
**Primary domain:** `samoips.rs`
**Source organization:** `github.com/samoips`
**Primary repository:** `github.com/samoips/samoips`
**Product type:** Static, local-first Progressive Web Application
**Primary market:** Serbia
**Primary interface language:** Serbian Latin
**Additional text support:** Serbian Cyrillic and other characters permitted by the NBS IPS format
**Backend:** None in the MVP
**Server-side database:** None in the MVP
**User account:** Not required
**Local persistence:** IndexedDB
**Payment processing:** Not provided

Suggested product description:

> **Samo IPS** is an open-source, local-first application for creating, importing, printing, and sharing one or more Serbian payment orders with NBS IPS QR codes.

Suggested Serbian tagline:

> **IPS uplatnice bez komplikacija.**

Expanded tagline:

> Kreirajte, odštampajte i podelite jednu ili više IPS uplatnica — ručno, iz tabele, aplikacije ili uz pomoć AI asistenta.

The application must clearly state that it is independent and is not operated, sponsored, certified, or endorsed by the National Bank of Serbia.

# 2. Current implementation baseline

The application already supports the following important capabilities:

* creation of Serbian payment orders through a web form;
* generation of NBS IPS QR codes;
* printable payment-slip rendering;
* multiple payment orders in one workspace;
* printing up to three payment slips on one A4 page;
* sharing several payment orders through one link;
* direct URL-based rendering of arbitrary NBS IPS payment-order strings;
* use by an AI assistant without browser-form automation.

The currently implemented machine interface accepts:

1. one or more complete NBS IPS textual strings;
2. joined using the LF newline character;
3. encoded as UTF-8;
4. Base64-encoded;
5. included as a versioned URL path parameter.

Example structure:

```text
https://samoips.rs/s/v1/<base64-payload>
```

Conceptual source data:

```text
K:PR|V:01|C:1|R:...|N:...|I:RSD...|P:...|SF:...|S:...|RO:...
K:PR|V:01|C:1|R:...|N:...|I:RSD...|P:...|SF:...|S:...|RO:...
```

This is already more than a sharing mechanism. It is a simple, deterministic machine interface that can be generated by:

* AI assistants;
* command-line scripts;
* spreadsheets;
* CRM systems;
* accounting software;
* browser extensions;
* third-party applications.

The MVP should formalize and document this interface rather than replacing it.

# 3. Product proposition

Samo IPS should not be positioned merely as another online IPS QR generator.

Its main proposition is:

> **Create, import, print, and share several Serbian payment orders through one privacy-oriented web application.**

Its strongest differentiators are:

* multiple payment orders per workspace;
* up to three payment slips per A4 page;
* one link containing several payment orders;
* stable URL-based machine input;
* local reusable recipients and templates;
* recurring payment-order drafts;
* Google Sheets, Excel, and CRM template-link generation;
* AI-assistant compatibility;
* offline operation;
* open-source implementation;
* no required account;
* no server-side payment database.

The product should be presented as useful to both ordinary users and automated systems:

> **IPS uplatnice za ljude, tabele, aplikacije i AI asistente.**

# 4. Problems addressed

Most simple IPS QR tools support only this workflow:

1. open a form;
2. enter one payment order;
3. generate one QR code;
4. print or download it.

Real Serbian payment workflows are often more complex.

Examples include:

* an accountant preparing several payment orders for one client;
* a landlord preparing rent and utility instructions every month;
* a school sending tuition, meals, excursions, and insurance payments;
* a sports club preparing monthly membership orders;
* a building manager generating orders for many apartment owners;
* a person preparing several payment slips for an older family member;
* a business keeping customer records in Google Sheets or a CRM;
* an AI assistant extracting payment details from a tax or accounting PDF;
* an application generating payment orders without integrating with a full API.

Samo IPS should address these workflows while remaining a payment-order preparation tool rather than becoming a bank, payment processor, accounting application, or invoicing platform.

# 6. Product principles

## 6.1 Local-first

Payment data should be processed locally in the browser whenever possible.

Core application use must not require payment data to be submitted to a backend.

## 6.2 No mandatory account

A user must be able to create, import, print, and share payment orders without registration.

## 6.3 Review before use

Samo IPS does not prove that:

* the recipient is legitimate;
* the account belongs to the displayed recipient;
* a tax or payment document is authentic;
* an AI assistant extracted the data correctly;
* the payment request is still current.

The application must always require or strongly encourage human review.

## 6.4 Deterministic machine input

The URL format and textual input format must be stable, documented, and versioned.

The same valid input must produce the same payment-order data.

## 6.5 Portable data

Users must be able to export and restore locally saved recipients, templates, recurrence rules, and settings.

## 6.6 Progressive complexity

A first-time user should immediately see a simple payment-order form.

Advanced functionality should be available but not obstruct basic use.

## 6.7 Honest security claims

Compression and Base64 encoding must not be described as encryption.

The application may be described as local-first or privacy-oriented only when the implementation supports those claims.

# 8. Main application modes

The main screen should expose three primary entry modes.

## 8.1 Create manually

The user fills in a structured Serbian payment-order form.

## 8.2 Paste or import IPS strings

The user pastes one or more complete NBS IPS textual payment orders.

Each order is placed on a separate line.

## 8.3 Open a generated link

A spreadsheet, script, CRM, or AI assistant constructs a versioned Samo IPS URL.

The application decodes, validates, and displays the included orders.

These three modes should converge into the same multi-order workspace.

# 10. NBS IPS textual input

The application should provide a dedicated text-input screen for advanced users and automated systems.

Example input:

```text
K:PR|V:01|C:1|R:640000001234567890|N:PRIMALAC|I:RSD2222,00|P:PLATILAC|SF:253|S:TEST|RO:971234
K:PR|V:01|C:1|R:160000001234567890|N:DRUGI PRIMALAC|I:RSD3500,00|P:PLATILAC|SF:289|S:ČLANARINA|RO:00123
```

Requirements:

* one complete payment order per line;
* LF used as the canonical separator;
* CRLF input accepted and normalized;
* blank lines ignored;
* whitespace around lines handled safely;
* original order retained;
* validation performed separately for each line;
* errors displayed next to the affected order;
* valid and invalid orders never silently merged.

Actions:

* Add valid orders to workspace;
* Replace current workspace;
* Download source text;
* Create a share link;
* Print valid orders;
* Copy normalized IPS strings.

This feature must be described as useful independently of AI.

# 11. URL-based machine interface

## 11.1 Current direct format

The existing interface should remain supported:

```text
/s/v1/<encoded-payment-orders>
```

Version 1 contains:

1. complete NBS IPS textual strings;
2. joined with LF;
3. encoded as UTF-8;
4. encoded using the documented Base64 variant;
5. included in the URL.

The exact Base64 variant must be documented.

For future compatibility, unpadded Base64url is preferable because it avoids `/`, `+`, and `=` routing complications. Existing Base64 links must continue to work.

## 11.2 Purpose

This route is intended for:

* AI assistants;
* scripts;
* spreadsheet formulas;
* CRM templates;
* accounting exports;
* third-party tools;
* debugging;
* interoperability testing.

## 11.3 Versioning

The application must never silently redefine `/s/v1/`.

Future incompatible formats must use another version:

```text
/s/v2/
/s/v3/
```

Old public links should remain usable wherever practical.

## 11.4 Practical limits

The application should support arbitrary-length lists at the data-model level, but public documentation must acknowledge practical URL-length limits imposed by:

* browsers;
* web servers;
* proxies;
* messaging services;
* email clients;
* QR encoders.

When a link becomes too long, the application should recommend:

* splitting the bundle;
* exporting a file;
* using the compressed sharing format.

# 12. Compact sharing links

## 12.1 Purpose

Compact sharing links are intended for human distribution through:

* messaging applications;
* email;
* documents;
* websites;
* QR codes;
* customer-management systems.

A sharing link may contain one or several payment orders.

## 12.2 Compression

The application may use its existing zstd-inspired compression scheme with a custom vocabulary trained on Serbian:

* toponyms;
* personal names;
* surnames;
* organization names;
* addresses;
* payment terminology;
* financial terminology;
* frequently repeated NBS IPS fields.

The compression dictionary and algorithm must be versioned.

## 12.3 Security description

The compressed format is not encryption.

The application should say:

> Podaci u linku koriste kompaktan format aplikacije i nisu neposredno čitljivi. Svako ko dobije ceo link ipak može otvoriti uplatnice.

It must not say:

* encrypted;
* confidential;
* impossible to decode;
* secure against someone possessing the link.

## 12.4 Path versus fragment

The existing path-based format can remain supported for compatibility and agent use.

However, the preferred human sharing format should use the URL fragment where practical:

```text
https://samoips.rs/#/s/v1/<payload>
```

or:

```text
https://samoips.rs/#s=<payload>
```

A fragment is normally processed by the browser and is not sent to the web server.

If path-based links remain the primary public format, the production deployment must:

* avoid logging full payload paths where possible;
* avoid third-party analytics;
* clearly disclose that the path may appear in infrastructure logs;
* never include payment payloads in error-reporting services.

## 12.5 Shared-link view

Opening a link should show:

* number of payment orders;
* validation status;
* recipient names;
* amounts;
* payment purposes;
* reference numbers;
* QR codes;
* print actions;
* import-to-workspace action.

Opening a shared link must not automatically save the orders into IndexedDB.

# 18. Spreadsheet and CRM template links

## 18.1 Purpose

Users should be able to keep person-related data in:

* Google Sheets;
* Microsoft Excel;
* CRM systems;
* accounting systems;
* custom databases.

Samo IPS then acts as a renderer.

## 18.2 Field categories

Each integration field may be:

### Locked

Defined by the template and not replaceable by external data.

Typical locked fields:

* recipient account;
* recipient name;
* payment code;
* model.

### Variable

Required from the spreadsheet or CRM.

Examples:

* payer name;
* address;
* amount;
* customer ID;
* reference number.

### Editable

Pre-filled externally but changeable after opening.

### Calculated

Derived through a limited, safe rule system.

Examples:

* payment purpose containing the month;
* reference generated from a member number;
* amount based on quantity.

Arbitrary JavaScript expressions must not be supported.

## 18.3 Integration wizard

The user flow should be:

1. Choose or create a payment template.
2. Mark each field as locked, variable, editable, or calculated.
3. Assign external field names.
4. Choose Google Sheets, Excel, or generic CRM.
5. Map spreadsheet columns or placeholders.
6. Generate a formula or URL template.
7. Test it with sample data.

## 18.4 Google Sheets

The application should generate a ready-to-paste `HYPERLINK` formula.

It should also provide:

* suggested column headers;
* an example data row;
* formula-fill instructions;
* validation guidance.

## 18.5 Excel

The application should generate an equivalent formula compatible with supported Excel versions.

Version-specific limitations must be disclosed.

## 18.6 Generic CRM

The application should generate a placeholder-based URL template appropriate for systems that support record-field interpolation.

External values must never be able to override locked fields.

# 19. AI-assistant integration

## 19.1 Positioning

Samo IPS may be described as:

* AI-assistant-friendly;
* agent-ready;
* usable by AI assistants;
* a deterministic renderer for NBS IPS payment orders.

It should not be described as:

* the first AI payment generator;
* an AI verification system;
* an application that guarantees correct PDF extraction;
* an autonomous payment agent.

Suggested statement:

> AI assistants can extract payment instructions from documents and create a Samo IPS link. Samo IPS validates and renders the resulting orders for human review.

## 19.2 AI workflow

The documented workflow is:

1. Read the source document.
2. Identify every complete payment order.
3. Extract values without guessing.
4. Construct one complete NBS IPS textual string per order.
5. Join the strings with LF.
6. Encode them according to the Samo IPS v1 specification.
7. Construct the URL.
8. Ask the user to verify every order.

## 19.3 Mandatory AI warning

When a link identifies itself as AI-generated, display:

> Podatke je izdvojio AI asistent. Pre štampanja ili plaćanja proverite račun, iznos, model i poziv na broj.

Optional provenance may include:

* source type;
* document name;
* page number;
* extraction date;
* assistant name.

Provenance metadata must not alter the NBS IPS payload.

# 23. Privacy model

## 23.1 Ordinary local use

The application should not send entered payment data to a server during:

* manual creation;
* QR generation;
* printing;
* local template use;
* local recurrence generation;
* local import and export.

## 23.2 Shared links

Users must understand that:

* anyone with the complete link can read the orders;
* Base64 is not encryption;
* compression is not encryption;
* links may remain in browser or message history;
* path-based payloads may be visible in infrastructure logs;
* forwarded links remain usable.

## 23.3 Third-party code

Pages processing payment data should avoid:

* third-party analytics;
* third-party fonts requiring runtime requests;
* external QR-generation services;
* advertising scripts;
* session-replay scripts;
* external error trackers containing URLs or form state.

Any analytics must exclude:

* full URLs;
* URL fragments;
* account numbers;
* payer names;
* recipient names;
* amounts;
* payment purposes;
* references;
* textual IPS strings.

# 28. Main user flows

# 29. MVP acceptance criteria

The MVP is ready for public release when all of the following are true.

## Core generation

* A user can create a valid payment order manually.
* A user can paste several NBS IPS strings.
* Every order is validated independently.
* QR codes are generated locally.
* Invalid data cannot silently appear valid.

## URL interface

* `/s/v1/` is documented and stable.
* Existing links continue to work.
* Multiple newline-separated orders decode correctly.
* Malformed payloads produce a safe error.
* Unsupported versions are reported clearly.
* Base64 behaviour is precisely documented.

## Multi-order support

* Orders can be added, edited, duplicated, deleted, reordered, and selected.
* Several orders can be included in one share link.
* Large-link warnings are provided.
* Invalid orders cannot be shared without an explicit warning.

## Printing

* One, two, or three orders can be printed per A4 page.
* Individual slips are never split across pages.
* QR codes remain sharp and scannable.
* Application UI does not appear in printed output.

## Local storage

* Recipients and templates persist across reloads.
* Users can search saved records.
* Users can export and restore local data.
* Local-storage limitations are disclosed.

## Recurrence

* Monthly recurring templates can be created.
* Due drafts appear when the application opens.
* Duplicate generation is prevented or warned about.
* No order is distributed automatically.

## Integration templates

* Locked fields cannot be overridden externally.
* Google Sheets formulas can be generated.
* Excel formulas can be generated or limitations clearly explained.
* Generic CRM URL templates can be generated.
* Generated links resolve into valid workspace orders.

## AI integration

* `/llms.txt` is available.
* Human-readable agent instructions are available.
* At least one tested AI prompt is published.
* AI-generated links display a review warning.
* The documentation instructs agents not to guess missing values.

## PWA

* The application is installable.
* Core functions work offline.
* Updates do not destroy unsaved work.
* Mobile and desktop layouts are usable.

## Privacy and security

* Ordinary local use does not transmit payment fields.
* Compression is never called encryption.
* Third-party scripts cannot collect payment payloads.
* A vulnerability-reporting method is published.
* A clear independent-service disclaimer is visible.

# 30. Deferred features

The following are explicitly post-MVP.

## Verified senders

A future backend may verify:

* email addresses;
* phone numbers;
* organizations;
* authorized representatives;
* recipient accounts.

Verification labels must state exactly what was verified.

## Cryptographic signatures

Future signed requests may include:

* issuer ID;
* verification level;
* issue time;
* expiration;
* payload hash;
* key identifier;
* ECDSA signature.

A signed template and a signed completed payment request must be presented as different trust levels.

## Automatic distribution

A future professional service may support:

* server-side schedules;
* automatic email delivery;
* expiry;
* revocation;
* audit history;
* failed-delivery notifications.

This requires a backend and accounts.

## Native applications

A Play Store wrapper may eventually package the PWA.

A fully native Android application should be built only when native functionality is needed.

An Electron application is not planned unless desktop-specific requirements emerge.

## APIs and agent tools

Possible future interfaces include:

* REST API;
* OpenAPI specification;
* MCP server;
* signed-request API;
* batch-validation API;
* organization integrations.

The versioned URL interface and `/llms.txt` are sufficient for the MVP.

# 32. Final product description

> **Samo IPS** is an open-source, local-first web application for creating, importing, printing, and sharing Serbian payment orders with NBS IPS QR codes.
>
> It supports one or several payment orders, prints up to three slips per A4 page, accepts complete NBS IPS strings through a documented versioned URL, and works with forms, spreadsheets, CRM systems, scripts, and AI assistants.
>
> Recipients, templates, and recurring drafts can be stored locally in the browser. No account or backend is required for the core application.
>
> Samo IPS does not perform payments, authenticate recipients, or guarantee the correctness of AI-extracted data. Users must verify all payment details before printing or confirming a payment in their banking application.
